# 작업 구현

사용자가 명세나 티켓에 기술한 작업을 구현한다.

## 계획 경계

이 스킬은 계획 계열 작업을 결코 수행하지 않는다. 트리아지, 탐색, 명세 작성이나 수정, 분해, 티켓 생성이나 분할, 티켓 게시, 계획 수정을 하지 않는다. 구현은 이미 합의된 명세나 티켓에서만 시작한다.

입력에 계획이 필요하거나, 계획이 잘못됐거나 명세가 불충분하면, 구현을 멈추고 작업을 호출자나 `/vibe-plan`/`/vibe-deep-plan`에 돌려보낸다. 이 스킬 안에서 계획을 고치거나 바꾸지 않는다.

## 완료 소유권

`vibe-implement`는 원자적 단일 티켓 실행만 한다. 모드를 나누지 않는다. 호출자(예: `vibe-goal`)가 원장/handoff로 할당 기록(작업 단위 ID, 원래 target/ref, fixed point, 브랜치, worktree 경로, 소유자/상태)을 공급하면 그 작업공간을 재사용하고, 공급이 없으면 아래 작업공간 격리 규칙에 따라 하나의 작업공간을 만든다. 같은 논리 작업의 구현 → 리뷰 → 발견사항 수정 → 재개는 그 정확히 하나의 작업공간을 재사용하며 두 번째 작업공간을 추가하지 않는다. 현재 worktree 경로(`.agents/worktrees/*`)나 브랜치 이름(`vibe/*`)만으로 상태를 추측하지 않는다. 이 스킬은 `vibe-goal` 내부의 `caller-supplied` 같은 모드 분기를 소유하지 않는다.

무엇이든 손대기 전에, 같은 논리 작업의 기존 **작업공간 기록**를 찾는다. 구현, 검토, 검토 결과 수정, 이전 실행 재개는 모두 같은 작업이다. 작업공간 기록은 작업 단위 ID를 원래 target/ref, fixed point, 브랜치, worktree 경로, 현재 소유자/상태와 묶는다. 이는 외부에서 공급한 할당 기록 또는 실행 자체의 이전 반환 기록에 있다. 일치하는 기록이 하나만 있고 다른 활성 소유자가 잡고 있지 않으면, 그대로 재사용한다. 기존 worktree에서 모든 작업을 계속하고, worktree가 제거됐으면 유지된 브랜치에 worktree를 다시 연결하고(새 번호 브랜치를 만들지 않는다), 원래 fixed point를 유지하고(현재 HEAD에서 다시 계산하지 않는다), 새 브랜치나 worktree를 만들지 않는다. 기록이 없거나, 후보가 여러 개이거나, 다른 활성 소유자가 있거나, 예상치 못한 head나 안전하지 않은 더티 상태가 있으면, 멈추고 보고한다. 브랜치 이름, 번호, slug, 최신 `vibe/*`로 추측하지 않고, 새 형제를 만들지 않는다. 매칭되는 기록이 없는 새 논리 작업일 때만, 현재 커밋(`git rev-parse HEAD`)을 검토가 실행될 **fixed point**로 캡처하고, 아래 작업공간 격리에 따라 하나의 작업공간을 만든 뒤 반환 결과에 기록한다.

## 작업공간 격리

변경 크기를 분류하기 전에, 완료 소유권의 기록 조회를 먼저 적용한다. 같은 논리 작업의 기존 작업공간 기록에 매칭됐으면, 변경 크기와 무관하게(한 줄 검토 결과 수정이나 재개도 포함) 모든 구현, 테스트, 검토 결과 수정, 재개를 그 정확한 작업공간(기존 worktree, 또는 유지된 브랜치에 worktree를 다시 연결)에서 계속하고 아래 선형성 규칙으로 건너뛴다. 그런 계속을 원래 checkout으로 보내지 않는다. 외부에서 할당 기록을 공급한 경우 그 기록이 식별한 작업공간만 사용하고 통합 브랜치는 절대 사용하지 않는다. 같은 논리 작업의 재시도에 두 번째 작업공간을 추가하지 않는다. 누락되거나 모호한 외부 공급 기록은 멈춤-보고 조건이지, 새 작업공간을 만드는 허가가 아니다. 매칭되는 기록이 없는 새 논리 작업이면, 요청된 변경을 분류한다. 단일 파일 변경이나 기타 사소한 변경은 격리 임계값 이하이므로 제자리에서 진행한다. 전용 worktree를 만들지 않는다. 매칭되는 기록이 없는 더 큰 변경의 경우, 프로젝트가 최소 하나의 커밋으로 git을 사용하면(`git rev-parse HEAD` 성공), 원래 checkout을 편집하는 대신 전용 worktree에 작업을 격리한다:

1. 브랜치 이름을 `vibe/{number}-{function}`로 짓는다. `{number}`는 기존 `vibe/*` 브랜치 중 다음 순차 번호(1부터 시작), `{function}`은 기능의 짧은 kebab-case slug(예: `vibe/3-user-auth`).
2. 생성: `git worktree add .agents/worktrees/{number}-{function} -b vibe/{number}-{function}`(fixed point에서 브랜치). `.agents/worktrees/`가 git-ignore 되어 있는지 확인한다.
3. 모든 구현, 테스트, 검토를 그 worktree 안에서 한다.
작업 브랜치를 구현 소스로 유지하고 원래 브랜치는 바꾸지 않는다. 같은 논리 작업(초기 구현, 검토 결과 수정, 모든 재개)은 기록이 식별한 하나의 작업공간을 재사용하며, 두 번째 브랜치나 worktree를 만들지 않는다. 계속되는 실행은 같은 작업에 새 `vibe/{next-number}-*` 브랜치를 만들지 않는다. 실행은 최대 하나의 브랜치와 최대 하나의 worktree를 만들고, 그 브랜치의 이력을 선형으로 유지한다. 원래 브랜치, 통합 브랜치, target을 작업 브랜치에 병합하지 않는다. base가 움직이면, 외부 공급 기록이 없으면 작업 브랜치를 그 위로 rebase하고, 외부 공급 기록이 있으면 직접 병합이나 rebase 대신 움직인 base를 호출자에게 보고한다. 외부에서 공급된 작업공간에서는 추가 브랜치나 worktree를 만들거나, 원래 target checkout을 수정하거나, 작업 브랜치를 게시하거나 병합하거나, 반환 후 그 worktree를 정리, 삭제, 기타 변경하지 않는다. 검토된 작업이 커밋된 후, 아래 완료 처분을 따른다. 자동으로 병합하지 않는다. 완료 반환에 작업공간(작업 단위 ID, 원래 target/ref, fixed point, 브랜치, worktree 경로, 소유자/상태)를 기록하여, 같은 논리 작업의 후속 review-fix나 재개가 새 작업공간을 만드는 대신 그것을 정확히 재사용하게 한다.

저장소에 아직 커밋이 없으면(또는 프로젝트가 git 저장소가 아니면), 격리를 건너뛰고 제자리에서 작업한다.

사전에 합의한 경계에서 테스트 우선으로 구현한다. [TDD.md](TDD.md)를 따른다. red → green 루프, 경계 규칙, 피해야 할 안티 패턴.

필요에 따라 읽는 참고 문서:

- [TDD.md](TDD.md) — red → green 루프와 그 규칙
- [tests.md](tests.md) — 좋은 테스트가 어떤 모습인지, 예시 포함
- [mocking.md](mocking.md) — 언제 모킹할지, 대신 무엇을 모킹할지
- [MERGE-CONFLICTS.md](MERGE-CONFLICTS.md) — 진행 중인 병합이나 리베이스 충돌 해결

타입 검사를 정기적으로, 단일 테스트 파일을 정기적으로, 전체 테스트 스위트는 마지막에 한 번 실행한다.

## 커밋 서명

이 워크플로의 커밋은 사람이 아닌 AI가 작성하므로, 사람이 만든 것처럼 서명해서는 안 된다. `git commit`에 `-S`, `--gpg-sign`, `--signoff`를 결코 전달하지 않는다. 저장소나 전역 설정이 기본적으로 서명을 켜면(`commit.gpgsign = true`), 커밋마다 `git -c commit.gpgsign=false commit …`로 덮어써 결과가 정직하게 서명되지 않게 한다. 이는 이 워크플로가 만드는 모든 커밋에 적용되며, 구현 커밋에 포함되는 체크박스 flip 편집도 포함한다.

## 완료 처분

1. `docs/agents/issue-tracker.md`를 읽는다.
2. 작업 브랜치에서, 시작 시 기록된 fixed point에 대해 `/vibe-review`를 실행하고, 구현된 명세나 티켓을 전달하여 켠 검토 축이 필요한 출처를 갖게 한다. Risk를 켤지는 `/vibe-review`의 위험 요청·고위험 변경 규칙을 그대로 따르며, 이 스킬이 별도 조건을 만들지 않는다. 사용자에게 fixed point를 묻지 않는다. 이미 알려져 있다. `/vibe-review`는 읽기 전용이다. 결과를 보고하지만 이슈 본문, 체크박스, 코멘트, 라벨, 상태를 결코 바꾸지 않는다. 통과한 검토는 이슈 닫기를 승인하지 않는다.
3. 읽기 전용 검토에 미해결 결과가 없으면, 검토된 작업을 작업 브랜치에 커밋한다. 인수 체크박스 flip([트래커 갱신](#트래커-갱신))은 이 처분의 일부이며, 사람이 머지하기 전에 끝낸다. 그다음 외부 공급 기록 유무에 따라 처분한다:
   - **외부 공급 기록이 있는 경우(예: `vibe-goal`이 공급한 할당 작업공간).** 공급된 작업 브랜치에 직접 커밋하고, 공급된 base 위에 선형으로 유지한다. 추가 브랜치나 worktree를 만들지 않는다. 작업 브랜치를 게시하거나, 지속 산물로 취급하거나, 직접 정리하지 않는다. 원래 target에 병합하거나 반영하지 않는다. 공급된 worktree를 정리, 삭제, 기타 변경하지 않는다. 호출자가 소유하고 처분한다. 호스티드 트래커에서는 [트래커 갱신](#트래커-갱신)에 따라 인수 체크박스만 켜고, 이슈를 닫거나 종료 상태를 바꾸지 않는다. 버전 관리되는 local Markdown 티켓 파일은 브랜치 내용이며 [트래커 갱신](#트래커-갱신)에 따라 티켓 커밋에 포함된다. 브랜치 이름, 정확한 공급된 티켓 base SHA, 정확한 검토된 head SHA, 검증 근거, 읽기 전용 `/vibe-review` verdict와 report, 공급된 base가 움직였으면 그에 대한 메모, 그리고 한 줄 재개 기록(작업 단위 ID, 작업 브랜치, worktree 경로, 현재 소유자/상태)을 반환한다. 이후 같은 티켓의 review-fix나 재시도가 새 브랜치나 worktree를 만드는 대신 이 정확한 작업공간을 재사용하게 한다. 그 외는 없다. 호출자가 통합과 최종 반영을 소유한다.
   - **외부 공급 기록이 없는 직접 호출.** 정확히 하나의 생존 브랜치와 남는 worktree 없이 끝낸다. 검토된 `vibe/*` 브랜치, fixed point 위에 선형. target이 움직이면 그 위로 rebase, 병합 커밋은 없다. 반영하는 대신 그 브랜치를 구현 소스로 유지한다. local Markdown 트래커의 경우, worktree를 제거하기 전에 병합되지 않은 브랜치가 유지됐음을 확인하고 브랜치 이름을 보고한다. GitHub의 경우 작업 브랜치를 push하고 원래 브랜치를 대상으로 pull request를 만든다. GitLab의 경우 push하고 원래 브랜치를 대상으로 merge request를 만든다. 호스티드 트래커에서는 게시 전에 [트래커 갱신](#트래커-갱신)에 따라 인수 체크박스를 켜고, [트래커 갱신](#트래커-갱신)의 네이티브 닫기 자격에 따라 PR/MR 본문에 닫기 참조 또는 닫기 키워드 없는 참조를 넣고, 게시 직후 target 브랜치와 닫기 대상 이슈 목록을 검증한다. 직접 이슈를 닫지 않으며, 자동으로 병합하지 않는다. pull/merge request를 지원하는 다른 호스티드 트래커의 경우, 문서화된 게시 워크플로를 따른다. 유지나 게시가 성공한 후에만 worktree를 제거한다. 유지된 브랜치 이름(호스티드 트래커의 경우 요청 URL)과 한 줄 재개 기록(작업 단위 ID, 원래 target/ref, fixed point, 유지된 브랜치, 제거되면 빈 worktree 경로, 현재 소유자/상태)을 보고한다. 이후 review-fix나 재개가 새 `vibe/*` 브랜치를 만드는 대신 그 정확한 유지된 브랜치에 worktree를 다시 연결하게 한다. 같은 실행에서 다른 `vibe/*` 브랜치나 worktree를 남기지 않는다. 자동으로 병합하지 않는다. 원래 브랜치는 바뀌지 않는다.

관련 없는 더티 상태, 충돌 불확실성, 또는 다른 안전하지 않은 조건이 안전한 처분을 막으면, 게시, 병합, 정리, 삭제를 하지 않는다. 원본과 결과 브랜치와 커밋을 보존하고, 사용자 상태를 손대지 않고, 차단 요소를 보고한다. 브랜치나 worktree 제거는 처분이 안전해진 후에만 허용된다. 진행 중인 병합이나 리베이스 충돌의 경우, [MERGE-CONFLICTS.md](MERGE-CONFLICTS.md)를 따른다.

## 트래커 갱신

- **Local Markdown, 버전 관리됨.** 티켓 파일은 외부 시스템이 아닌 브랜치 내용이다. 작업 브랜치의 worktree 안에서, 인수 체크박스를 `[X]`로 바꾸고 그 편집을 구현과 같은 커밋에 포함한다. 별도 트래커 커밋, 코멘트, 원래나 target 브랜치의 커밋은 없다. 반영 증명을 기다리지 않고, tracker-change 승인을 요구하지 않는다. 사용자가 병합을 소유하며, 병합은 코드와 체크리스트를 함께 또는 둘 다 없다. `상태:` 줄을 바꾸지 않는다.
- **호스티드 트래커(GitHub, GitLab, 기타 호스티드 트래커).** 인수 체크리스트와 이슈 닫기는 별개다. 머지는 사람이 하며 에이전트가 하지 않는다. 게시는 반영이 아니다.
  - **체크리스트.** 읽기 전용 검토에 미해결 결과가 없으면, 외부 공급 기록이 없는 직접 호출에서는 PR/MR 게시 전에, 외부 공급 기록이 있는 호출에서는 호출자 반환 전에, 해당 티켓의 인수 체크박스를 켠다. 반영 증명을 기다리지 않고, 체크박스 전용 승인을 요구하지 않는다. 에이전트가 직접 이슈를 닫지 않는다 — 자격 있는 PR/MR에서는 사람이 UI에서 머지할 때 provider가 네이티브 자동 close를 수행한다.
  - **네이티브 닫기 자격.** 외부 공급 기록이 없는 직접 호출이고, PR/MR의 target이 provider default 브랜치이며, 머지로 인수가 끝나는 정확한 구현 티켓 하나일 때만 자격이 있다. 부모 명세 이슈는 결코 닫기 대상이 아니다. 명세와 유일한 티켓이 같은 이슈로 접혀 있으면 그 이슈 자체가 티켓이므로 자격이 있다. 외부 공급 기록이 있는 호출은 게시하지 않으므로 닫기 참조를 쓰지 않는다.
  - **자격 있는 닫기.** 설정된 트래커 참고 문서의 자동 close 참조 게시 규칙이 문서화한 닫기 참조 구문으로 그 정확한 티켓 하나를 PR/MR 본문에 연결한다. 게시 직후 같은 참고 문서의 게시 뒤 대상 검증 명령을 그 문서에 적힌 그대로 실행해, target 브랜치가 default 브랜치이고 닫기 대상이 그 티켓 정확히 하나인지 확인한다. provider별 명령과 그 정확한 플래그, 확인할 필드는 그 참고 문서가 단일 출처다 — 이 문서는 provider 명령을 복제하지 않으며, 기억이나 추측으로 만든 명령으로 대체하지 않는다. 검증이 어긋나거나 의도하지 않은 이슈가 딸려 오면, 반환 전에 본문을 고쳐 다시 검증하거나, 안전하게 멈추고 브랜치·커밋·PR/MR을 보존한 채 차단 요소를 보고한다. 검증되지 않은 상태로 반환하지 않는다. 사람이 UI에서 Merge를 누르는 행위가 닫기 승인이므로, 머지 뒤에 별도의 닫기 미리보기나 별도 승인을 요구하지 않는다. 에이전트는 직접 머지하지 않고 직접 이슈를 닫지도 않는다. 통과한 검토만으로는 닫기가 승인되지 않는다.
  - **자격 없을 때의 fallback.** target이 default 브랜치가 아니거나, 머지 뒤에도 운영·배포 게이트가 남았거나, 부모 이슈나 여러 목표가 섞여 대상이 모호하면, 닫기 키워드 없는 참조만 넣고 네이티브 닫기를 쓰지 않는다. 그런 티켓의 닫기는 머지 게이트가 아니다. 독립적으로 정확한 검토된 커밋 SHA가 지정된 target 브랜치에 있음을 나타내는 권위 있는 증거(예: `git merge-base --is-ancestor <commit> <target-branch>` 성공)를 얻은 후에만, 후속 또는 재개 직접 호출에서 닫기·상태·코멘트의 정확한 미리보기를 보여주고 작성 직전에 별도의 명시적 승인을 기다린다. 구현 요청, 완료된 검토, 거절, 또는 무응답은 닫기 승인이 아니다. 승인 없이 이슈를 닫지 않는다.

어떤 트래커에서도 부모 명세 이슈를 제안하거나 수정하지 않는다. 호스트형에서 명세와 유일한 티켓이 같은 이슈이면 그것은 티켓이다 — 인수 체크박스는 그 이슈에서 켠다.
