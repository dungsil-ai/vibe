# 코드베이스 아키텍처 개선

**한국어 저장소 글:** 이 스킬이 한국어 문서, 커밋 메시지, 이슈, PR, 리뷰 또는 댓글을 작성하거나 다듬을 때에는 저장하거나 전송하기 전에 `/vibe-docs`를 적용한다. `/vibe-docs`는 표현만 다루며, 이 스킬의 권한이나 외부 변경 범위를 넓히지 않는다.

아키텍처 마찰을 드러내고 **심화 기회** — 얕은 모듈을 깊은 모듈로 바꾸는 리팩터 — 를 제안한다. 목표는 테스트 용이성과 AI 탐색 용이성이다.

이 명령은 프로젝트의 도메인 모델에 _기반_ 하며, 공유 설계 어휘 위에서 작동한다:

- 아키텍처 개념은 [VOCABULARY.md](VOCABULARY.md)를 본다 (모듈, 인터페이스, 깊이, 경계, 어댑터) — 그리고 원칙(삭제 테스트, "인터페이스가 테스트하는 면이다", "어댑터가 하나면 경계를 만들지 마라"). 사용자에게 보이는 글에는 그 말로 써라. `seam`, `leverage`, `locality`를 쓰지 마라. `component`, `service`, `API`로 빠지지 마라.
- `CONTEXT.md`의 도메인 언어는 좋은 경계에 이름을 붙여준다. `docs/adr/`의 ADR은 이 명령이 다시 논쟁해서는 안 되는 결정을 기록한다.

## 과정

### 1. 탐색

**스캔하기 전에 범위를 정하라 — YAGNI.** 모듈을 심화하는 보상은 해당 모듈의 향후 변경을 쉽게 만드는 데서 나오므로, 최근에 변경된 코드베이스 부분에 가중치를 둔다. 들여다보기 *전에* 들여다볼 곳을 정하라:

- 사용자가 방향을 지정했다면 — 모듈, 하위 시스템, 문제 지점 — 그것을 따르고, 아래 추론은 건너뛰어라.
- 그렇지 않으면 커밋 기록의 꽤 긴 구간(`git log --oneline`)을 되짚어 코드베이스의 핫스팟 — 반복적으로 등장하는 파일과 영역 — 을 찾고, 그 경로가 먼저 주의를 끌도록 하라. 변경이 흩어져 뚜렷한 핫스팟이 없다면 그물을 넓혀라.

먼저 프로젝트의 도메인 용어집(`CONTEXT.md`)과 다룰 영역의 ADR을 읽어라.

그런 다음 Agent 도구를 `subagent_type=Explore`로 사용해 코드베이스를 걸어라. 딱딱한 휴리스틱을 따르지 마라 — 유기적으로 탐색하며 마찰을 겪는 곳을 기록하라:

- 하나의 개념을 이해하기 위해 여러 작은 모듈 사이를 오가야 하는 곳은 어디인가?
- 모듈이 **얕은** 곳 — 인터페이스가 구현만큼이나 복잡한 곳 — 은 어디인가?
- 테스트 가능성 때문에 순수 함수만 추출해 놓았지만, 진짜 버그는 호출 방식에 숨어 있는 곳(고칠 곳이 한곳에 없는 곳)은 어디인가?
- 긴밀히 결합된 모듈이 경계 너머로 새어나오는 곳은 어디인가?
- 코드베이스 중 테스트되지 않았거나 현재 인터페이스로 테스트하기 어려운 부분은 어디인가?

얕다고 의심되는 모든 것에 **삭제 테스트**를 적용하라: 삭제하면 복잡성이 집중되는가, 아니면 옮기기만 하는가? "집중된다"가 원하는 신호다.

후보의 의존성이 심화 및 테스트 방식을 결정할 때, 의존성 분류와 경계 규칙, "덧씌우지 말고 교체하라"는 테스트 방침은 [DEEPENING.md](DEEPENING.md)을 본다.

### 2. 후보를 HTML 보고서로 제시

저장소에 아무것도 남기지 않도록 자체 완결 HTML 파일을 OS 임시 디렉터리에 쓴다. 임시 디렉터리는 `$TMPDIR`에서 확인하고, 없으면 `/tmp`(또는 Windows에서 `%TEMP%`)로 대체하며, `<tmpdir>/architecture-review-<timestamp>.html`에 써서 매 실행마다 새 파일이 생기게 한다. 사용자에게 열어 보여라 — Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>` — 그리고 절대 경로를 알려 준다.

보고서는 레이아웃과 스타일에 **Tailwind(CDN)** 를, 그래프/플로우/시퀀스가 구조를 명확히 전달할 때 **Mermaid(CDN)** 를 다이어그램에 쓴다. Mermaid와 손으로 만든 CSS/SVG 시각화를 섞어라 — 관계가 그래프 모양(호출 그래프, 의존성, 시퀀스)일 때 Mermaid를, 편집적인 느낌(매스 다이어그램, 단면도, 접기 애니메이션)이 필요할 때 손으로 만든 div/SVG를 써라. 각 후보에는 **전/후 시각화**가 있다. 시각적으로 만들어라. 보고서는 한국어로 쓴다.

각 후보마다 다음을 담은 카드를 렌더링한다:

- **파일** — 관련 파일/모듈
- **문제** — 현재 아키텍처가 마찰을 일으키는 이유
- **해결** — 무엇이 바뀔지 평이한 한국어로 설명
- **이점** — 고칠 곳이 한곳인지, 인터페이스 하나로 여러 호출을 처리하는지, 테스트가 어떻게 나아지는지
- **전/후 다이어그램** — 나란히, 손으로 그려, 얕음과 심화를 보여준다
- **권고 강도** — `추천`, `검토`, `불확실` 중 하나, 배지로 렌더링

보고서 끝에 **최우선 권고** 섹션을 둔다: 가장 먼저 다루겠다는 후보와 그 이유.

**도메인에는 CONTEXT.md의 어휘를, 아키텍처에는 [VOCABULARY.md](VOCABULARY.md)의 한국어 풀어쓰기를 써라.** `CONTEXT.md`가 `주문 (Order)`를 정의한다면 "FooBarHandler"나 "Order service"가 아니라 "주문 접수 모듈"이라고 말하라.

**ADR 충돌**: 후보가 기존 ADR과 모순될 때, 마찰이 ADR을 재검토할 만큼 실재할 때만 드러내라. 카드에 명확히 표시하라 (예: 경고 콜아웃: _"ADR-0007과 충돌 — 하지만 재검토할 가치가 있는 이유는…"_). ADR이 금지하는 모든 이론적 리팩터를 나열하지 마라.

전체 HTML 뼈대와 다이어그램 패턴, 스타일 안내는 [HTML-REPORT.md](HTML-REPORT.md)를 본다.

아직 인터페이스를 제안하지 마라. 파일을 쓴 뒤 사용자에게 묻는다: "이 중 어느 것을 탐색해 보겠습니까?"

### 3. 집중 탐구 루프

사용자가 후보를 고르면, `/vibe-grilling` 스킬을 실행해 결정 트리를 함께 걷는다 — 제약, 의존성, 깊어진 모듈의 형태, 경계 뒤에 있는 것, 살아남는 테스트.

결정이 굳어지는 대로 인라인으로 부수 효과가 일어난다 — 진행하며 `/vibe-modeling` 스킬을 실행해 도메인 모델을 최신으로 유지한다:

- **`CONTEXT.md`에 없는 개념으로 깊어진 모듈에 이름을 붙이는가?** `CONTEXT.md`에 용어를 추가하라. 파일이 없으면 느리게 생성하라.
- **대화 중 흐린 용어를 명확히 다듬는가?** 그 자리에서 `CONTEXT.md`를 갱신하라.
- **사용자가 짐을 싣는 이유로 후보를 거절하는가?** ADR을 제안하라, 이렇게: _"이것을 ADR로 기록하여 향후 아키텍처 검토에서 다시 제안하지 않게 할까요?"_ 미래 탐색자가 같은 것을 다시 제안하지 않으려면 이유가 실제로 필요할 때만 제안하라 — 일시적 이유("지금은 가치 없음")와 자명한 이유는 건너뛰어라.
- **깊어진 모듈의 대안 인터페이스를 탐구하고 싶은가?** [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)의 design-it-twice 병렬 sub-agent 패턴을 써라.
