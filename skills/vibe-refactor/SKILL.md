# 코드베이스 아키텍처 심화

아키텍처 마찰을 드러내고 **심화 기회**(얕은 모듈을 깊은 모듈로 바꾸는 리팩터)를 제안한다. 목표는 테스트 용이성과 AI 탐색 용이성이다.

이 명령은 프로젝트의 도메인 모델에 _기반_ 하며, 공유 설계 어휘 위에서 작동한다:

- 아키텍처 개념은 [VOCABULARY.md](VOCABULARY.md)를 본다 (모듈, 인터페이스, 깊이, 경계, 어댑터). 원칙(삭제 테스트, "인터페이스가 테스트하는 면이다", "어댑터가 하나면 경계를 만들지 마라")도 본다. 사용자에게 보이는 글에는 그 말로 쓴다. `seam`, `leverage`, `locality`를 쓰지 않는다. `component`, `service`, `API`를 대체어로 쓰지 않는다.
- `CONTEXT.md`의 도메인 언어는 좋은 경계에 이름을 붙여준다. `docs/adr/`의 아키텍처 결정 기록(ADR)은 이 명령이 다시 논쟁해서는 안 되는 결정을 기록한다.

## 과정

### 1. 탐색

**스캔하기 전에 범위를 정한다. 필요하지 않은 기능은 만들지 않는다(YAGNI).** 모듈을 심화하면 그 모듈의 향후 변경이 쉬워진다. 커밋 기록에서 변경 순서가 더 최신인 코드 영역에 더 큰 비중을 둔다. 들여다볼 곳을 먼저 정한다:

- 사용자가 방향(모듈, 하위 시스템, 문제 지점)을 지정했다면 그 방향을 따른다. 아래 추론은 건너뛴다.
- 그렇지 않으면 커밋 기록의 충분히 긴 구간(`git log --oneline`)을 되짚어 코드베이스의 핫스팟(반복해서 등장하는 파일과 영역)을 찾는다. 그 경로를 먼저 살펴본다. 변경이 둘 이상의 경로에 흩어져 뚜렷한 핫스팟이 없다면 조사할 기간과 경로를 넓힌다.

먼저 프로젝트의 도메인 용어집(`CONTEXT.md`)과 다룰 영역의 ADR을 읽는다.

그런 다음 Agent 도구를 `subagent_type=Explore`로 사용해 코드베이스를 읽는다. 고정된 규칙을 따르지 않는다. 정해진 순서 없이 탐색하면서 마찰이 있는 곳을 기록한다:

- 하나의 개념을 이해하기 위해 둘 이상의 작은 모듈 사이를 오가야 하는 곳은 어디인가?
- 모듈이 **얕은** 곳(인터페이스가 구현만큼이나 복잡한 곳)은 어디인가?
- 테스트 가능성을 위해 순수 함수만 추출해 놓은 곳은 어디인가? 진짜 버그는 호출 방식에 숨어 있고, 고칠 곳이 한곳에 없는가?
- 긴밀히 결합된 모듈이 경계 너머로 새어나오는 곳은 어디인가?
- 코드베이스에서 테스트하지 않았거나 기존 인터페이스로 테스트하기 어려운 부분은 어디인가?

얕다고 의심되는 모든 것에 **삭제 테스트**를 적용하라: 삭제하면 복잡성이 집중되는가, 아니면 옮기기만 하는가? "집중된다"가 원하는 신호다.

후보의 의존성이 심화 및 테스트 방식을 결정할 때, 의존성 분류와 경계 규칙, "덧씌우지 말고 교체하라"는 테스트 방침은 [DEEPENING.md](DEEPENING.md)을 본다.

### 2. 후보를 HTML 보고서로 제시

저장소에는 아무것도 남기지 않는다. 에이전트는 다른 파일 없이 열리는 HTML 파일 하나를 OS 임시 디렉터리에 쓴다. 에이전트는 임시 디렉터리를 `$TMPDIR`에서 확인한다. `$TMPDIR`이 없으면 `/tmp` 또는 Windows의 `%TEMP%`를 임시 디렉터리로 쓴다.

에이전트는 `<tmpdir>/architecture-review-<timestamp>.html`에 파일을 쓴다. 매 실행마다 새 파일을 만든다. 에이전트는 사용자에게 파일을 열어 보여준다(Linux는 `xdg-open <path>`, macOS는 `open <path>`, Windows는 `start <path>`). 에이전트는 절대 경로를 알려 준다.

레이아웃과 스타일에는 **Tailwind(CDN)** 를 쓴다. 구조를 명확히 전달할 때 그래프, 흐름도 또는 시퀀스 다이어그램을 **Mermaid(CDN)** 로 그린다. Mermaid와 손으로 만든 CSS 및 SVG 시각화를 함께 사용한다. 호출 그래프, 의존성 또는 시퀀스처럼 그래프 모양의 관계는 Mermaid로 그린다.

매스 다이어그램, 단면도, 접기 애니메이션처럼 편집적 표현이 필요하면 손으로 만든 `div`나 SVG를 쓴다. 각 후보에는 **전과 후 다이어그램**이 있다. 다이어그램을 시각적으로 만든다. 보고서는 한국어로 쓴다.

각 후보마다 다음을 담은 카드를 렌더링한다:

- **파일**: 검토할 파일과 모듈
- **문제**: 기존 아키텍처가 마찰을 일으키는 이유
- **해결**: 무엇이 바뀔지 평이한 한국어로 설명
- **이점**: 고칠 곳이 한곳인지, 인터페이스 하나로 둘 이상의 호출을 처리하는지, 테스트가 어떻게 나아지는지
- **전과 후 다이어그램**: 나란히, 손으로 그려, 얕음과 심화를 보여준다
- **권고 강도**: `추천`, `검토`, `불확실` 중 하나, 배지로 렌더링

보고서 끝에 **최우선 권고** 섹션을 둔다. 이 섹션에는 가장 먼저 다룰 후보와 그 이유를 쓴다.

**도메인에는 `CONTEXT.md`의 어휘를, 아키텍처에는 [VOCABULARY.md](VOCABULARY.md)의 한국어 풀어쓰기를 쓴다.** `CONTEXT.md`가 `주문 (Order)`를 정의한다면 "FooBarHandler"나 "Order service"가 아니라 "주문 접수 모듈"이라고 말한다.

**ADR 충돌**: 후보가 기존 ADR과 모순될 때, 마찰이 ADR을 재검토할 만큼 실재할 때만 드러낸다. 카드에 명확히 표시한다 (예: 경고 콜아웃: _"ADR-0007과 충돌. 하지만 재검토할 가치가 있는 이유는…"_). ADR이 금지하는 모든 이론적 리팩터를 나열하지 않는다.

전체 HTML 뼈대와 다이어그램 패턴, 스타일 안내는 [HTML-REPORT.md](HTML-REPORT.md)를 본다.

아직 인터페이스를 제안하지 않는다. 파일을 쓴 뒤 사용자에게 묻는다: "이 중 어느 것을 탐색해 보겠습니까?"

### 3. 집중 탐구 루프

사용자가 후보를 고르면 `vibe-grilling` 스킬을 로드해 실행한다. 사용자와 결정 트리를 따라가며 제약, 의존성, 깊어진 모듈의 형태, 경계 뒤에 둘 내용, 구현이 바뀌어도 통과해야 할 테스트를 검토한다.

결정이 확정되는 대로 에이전트가 아래 항목을 바로 처리한다. 이 과정에서 `vibe-modeling` 스킬을 로드해 도메인 모델을 최신으로 유지한다:

- **`CONTEXT.md`에 없는 개념으로 깊어진 모듈에 이름을 붙이는가?** `CONTEXT.md`에 용어를 추가한다. 파일이 없으면 필요할 때 만든다.
- **대화 중 흐린 용어를 명확히 다듬는가?** 그 자리에서 `CONTEXT.md`를 갱신한다.
- **사용자가 이후 설계에도 계속 영향을 미칠 이유로 후보를 거절하는가?** 미래 탐색자가 같은 것을 다시 제안하지 않도록 이유를 남길 필요가 실제로 있을 때만 ADR을 제안한다. 일시적 이유("지금은 가치 없음")와 자명한 이유는 건너뛴다. 제안 문구는 다음과 같다: _"이것을 ADR로 기록하여 향후 아키텍처 검토에서 다시 제안하지 않게 할까요?"_
- **깊어진 모듈의 대안 인터페이스를 탐구하고 싶은가?** [DESIGN-IT-TWICE.md](DESIGN-IT-TWICE.md)에 정의한 병렬 하위 에이전트 방식을 쓴다.
