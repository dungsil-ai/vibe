# 두 번 설계하기

사용자가 고른 심화 후보의 다른 인터페이스를 비교할 때 병렬 하위 에이전트 패턴을 사용한다. "Design It Twice"(Ousterhout)에 기반한다. 첫 아이디어가 최고일 가능성은 낮다.

[VOCABULARY.md](VOCABULARY.md)의 말(**모듈**, **인터페이스**, **경계**, **어댑터**)을 쓴다. 비교문은 쉬운 한국어로 쓴다.

## 과정

### 1. 문제 공간을 정의한다

하위 에이전트를 만들기 전에 고른 후보의 문제 공간을 사용자에게 설명한다:

- 새 인터페이스가 지켜야 할 제약
- 의존성과 그 분류([DEEPENING.md](DEEPENING.md) 참조)
- 제약을 구체적으로 만드는 대략적인 예시 코드(제안이 아니라 제약을 분명히 하는 수단)

이 내용을 사용자에게 보여 준 뒤 2단계로 바로 이동한다. 사용자는 하위 에이전트가 병렬로 일하는 동안 이를 읽는다.

### 2. 하위 에이전트 생성

Agent 도구로 하위 에이전트를 3명 이상 병렬로 만든다. 각 하위 에이전트는 깊어진 모듈의 인터페이스를 서로 크게 다르게 설계한다.

각 하위 에이전트에 별도의 기술 브리프(파일 경로, 결합, [DEEPENING.md](DEEPENING.md)의 의존성 분류, 경계 뒤에 있는 것)를 준다. 브리프는 1단계의 사용자용 설명과 별개다. 각 하위 에이전트에 서로 다른 제약을 준다:

- Agent 1: "인터페이스를 최소화한다(진입점을 최대 1-3개로 제한한다). 진입점마다 처리하는 일을 늘린다."
- Agent 2: "유연성을 최대로 높인다. 둘 이상의 사용 사례와 확장 방식을 지원한다."
- Agent 3: "가장 흔한 호출자에 맞춘다. 기본 사례를 자명하게 만든다."
- Agent 4 (경계 너머 의존성이 있을 때만): "경계 너머 의존성을 포트와 어댑터로 설계한다."

각 하위 에이전트가 이름을 올바르게 붙일 수 있도록 브리프에 [VOCABULARY.md](VOCABULARY.md)와 `CONTEXT.md`의 어휘를 넣는다.

각 하위 에이전트의 출력:

1. 인터페이스(타입, 메서드, 매개변수, 그리고 불변 조건, 순서, 오류)
2. 호출자가 어떻게 쓰는지 보여주는 예
3. 경계 뒤에 구현이 숨기는 것
4. 의존성 전략과 어댑터([DEEPENING.md](DEEPENING.md) 참조)
5. 트레이드오프: 인터페이스 하나로 둘 이상의 호출을 처리하는 곳, 얇은 곳

### 3. 제시와 비교

각 설계를 하나씩 보여 준다. 깊이, 고칠 곳이 한곳인지, 경계 위치를 기준으로 산문으로 비교한다. `depth`, `locality`, `seam`을 쓰지 않는다.

비교한 뒤 권고를 제시한다. 어느 설계가 더 나은지와 그 이유를 설명한다. 두 설계를 잘 결합할 수 있으면 하이브리드를 제안한다. 권고에는 주관적인 판단을 담는다. 사용자는 선택지 목록이 아니라 판단을 원한다.
