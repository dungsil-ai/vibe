# 깊은 모듈 어휘

**깊은 모듈**은 많은 동작을 작은 인터페이스 뒤에 숨긴다. 모듈의 경계를 명확하게 정한다. 인터페이스를 통해 모듈을 테스트한다. 목표는 인터페이스 하나로 둘 이상의 호출을 처리하고, 고칠 곳을 한곳으로 모아 테스트하기 쉽게 만드는 것이다.

사용자에게 보이는 글(HTML 보고서, 카드, 질문, 범례)에는 아래 용어를 쓴다. `seam`, `leverage`, `locality`, `depth`, `golden` 같은 영어 전문용어를 라벨로 쓰지 않는다. 모듈, 인터페이스, 어댑터, 경계처럼 한국에서 그 뜻으로 쓰는 말만 쓴다. 새 번역 용어를 만들지 않는다.

## 용어집

**모듈**은 인터페이스와 구현이 있는 모든 단위를 가리킨다. 함수, 클래스, 패키지, 계층을 가로지르는 단위도 모듈이다. unit, component, service는 피할 말이다.

**인터페이스**는 호출자가 모듈을 쓰려면 알아야 하는 모든 정보를 뜻한다. 그 범위에는 타입뿐 아니라 불변 조건, 순서, 오류, 설정, 성능도 포함한다. API와 signature는 피할 말이다. signature는 타입만 가리킨다.

**구현**은 모듈 안의 코드다. 구현은 **어댑터**와 다르다. 작은 어댑터는 큰 구현을 감쌀 수 있고(Postgres repository), 큰 어댑터는 작은 구현을 감쌀 수도(메모리 대역) 있다. 경계를 설명할 때는 "어댑터"라는 용어를 쓴다. 그 밖에는 "구현"이라는 용어를 쓴다.

**깊이**는 호출자가 알아야 하는 인터페이스의 크기에 비해 모듈이 실행하는 동작이 얼마나 많은지를 나타낸다. 작은 인터페이스 뒤에 동작이 많으면 **깊다**. 인터페이스가 구현만큼 복잡하면 **얕다**. 사용자에게 보이는 글에는 "깊다", "얕다"라고 쓴다. `depth`라고 쓰지 않는다.

**경계**는 모듈의 인터페이스가 있는 곳을 가리킨다. 그 인터페이스를 바꾸지 않고도 동작을 바꿀 수 있다. 경계를 어디에 둘지는 그 뒤에 무엇을 넣을지와 별개의 결정이다. 사용자에게 보이는 글에서는 "경계"만 쓴다. `seam`이라고 쓰지 않는다. 도메인 주도 설계(DDD)의 bounded context는 "바운디드 컨텍스트"라고 써서 이 경계와 섞지 않는다.

**어댑터**는 경계에서 인터페이스를 채우는 구현을 가리킨다. 어댑터라는 말은 그 역할(어느 칸인지)을 나타내지만, 구현 안의 내용은 나타내지 않는다.

호출자가 깊이에서 얻는 이점과 고치는 사람이 깊이에서 얻는 이점을 새 명사로 부르지 않는다. "인터페이스 하나로 둘 이상의 호출을 처리한다", "고칠 곳이 한곳이다"처럼 문장으로 쓴다.

## 깊음과 얕음

**깊은 모듈**은 작은 인터페이스와 많은 동작으로 이뤄진다.

```
┌─────────────────────┐
│   작은 인터페이스    │  ← 메서드 적음, 매개변수 단순
├─────────────────────┤
│                     │
│  깊은 구현           │  ← 복잡한 로직을 숨김
│                     │
└─────────────────────┘
```

**얕은 모듈**은 큰 인터페이스와 적은 구현으로 이뤄지므로 피한다.

```
┌─────────────────────────────────┐
│       큰 인터페이스              │  ← 메서드 많음, 매개변수 복잡
├─────────────────────────────────┤
│  얇은 구현                       │  ← 전달만 함
└─────────────────────────────────┘
```

인터페이스를 설계할 때 다음을 묻는다:

- 메서드 수를 줄일 수 있는가?
- 매개변수를 단순화할 수 있는가?
- 더 많은 복잡성을 안에 숨길 수 있는가?

## 원칙

- **깊이는 구현이 아니라 인터페이스의 속성이다.** 깊은 모듈의 구현은 작고 다른 구현으로 바꿀 수 있어도 된다. 다만 그 구현은 공개 인터페이스가 아니다. 모듈은 공개 **바깥 경계** 외에, 자기 테스트만 쓰는 **안쪽 경계**를 가질 수 있다.
- **삭제 테스트.** 모듈을 지운다고 상상한다. 복잡성이 사라지면 통과형이다. 모듈을 지웠을 때 둘 이상의 호출자가 복잡성을 다시 다뤄야 한다면 모듈이 필요하다.
- **"인터페이스가 테스트하는 면이다"**. 테스트는 인터페이스를 통해서만 모듈에 닿는다. 호출자와 테스트는 같은 경계를 지난다. 인터페이스 *너머*를 테스트하고 싶다면 모듈 형태가 잘못된 경우가 많다.
- **"어댑터가 하나면 경계를 만들지 마라"**. 둘(보통 프로덕션과 테스트)일 때만 경계를 둔다.

## 테스트하기 쉽게 설계하기

1. **의존성을 만들지 않고 받는다.**

   ```typescript
   // 테스트 가능
   function processOrder(order, paymentGateway) {}

   // 테스트 어려움
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **부수 효과를 만들지 않고 결과를 반환한다.**

   ```typescript
   // 테스트 가능
   function calculateDiscount(cart): Discount {}

   // 테스트 어려움
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **인터페이스를 작게 만든다.** 메서드가 적으면 테스트도 적다. 매개변수가 단순하면 준비도 단순하다.

## 관계

- **모듈**은 **인터페이스**를 하나 가진다.
- **깊이**는 그 인터페이스로 잰다.
- **경계**는 그 인터페이스가 있는 곳이다.
- **어댑터**는 경계에서 인터페이스를 채운다.
- 깊으면 호출자는 인터페이스 하나로 더 많은 일을 하고, 고치는 사람은 한곳만 보면 된다.

## 쓰지 말 것

- **구현 줄 수 대비 인터페이스 줄 수로 깊이를 재기** (Ousterhout): 이 기준은 구현 줄 수를 필요 이상으로 늘린다. 호출자가 얻는 이점으로 깊이를 잰다.
- **TypeScript `interface`나 public 메서드만 "인터페이스"로 보기**: 호출자가 알아야 할 사실을 모두 포함한다.
- **영어 전문용어를 라벨로 붙이기** (`seam`, `leverage`, `locality`, `depth`, `golden`).
- **새 번역 명사 만들기** (이음새, 한곳 모임, 호출자 이득). 이미 쓰는 말과 문장으로 풀어 쓴다.
