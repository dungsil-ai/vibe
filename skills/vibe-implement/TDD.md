# 테스트 주도 개발

테스트 주도 개발(TDD)은 red → green 루프다. 이 문서는 루프를 유지할 만한 테스트를 만드는 방법을 설명한다. 좋은 테스트의 조건, 테스트를 둘 위치, 안티 패턴, 루프의 규칙을 다룬다. 모든 섹션은 매 사이클에 적용된다. 루프를 마친 뒤가 아니라 루프 전과 진행 중에 참고한다.

코드베이스를 탐색할 때 `CONTEXT.md`가 있으면 읽는다. 테스트 이름과 인터페이스 어휘는 프로젝트의 도메인 언어에 맞춘다. 작업 중인 영역의 아키텍처 결정 기록(ADR)을 준수한다.

## 좋은 테스트란 무엇인가

테스트는 구현 세부사항이 아니라 공개 인터페이스로 행동을 검증한다. 코드가 완전히 바뀌어도 테스트는 그대로 유지한다. 좋은 테스트는 명세처럼 읽힌다. "user can checkout with valid cart"는 어떤 기능이 있는지 정확하게 알려준다. 테스트는 내부 구조에 의존하지 않으므로 리팩터링을 견딘다.

예시는 [tests.md](tests.md)를, 모킹 지침은 [mocking.md](mocking.md)를 참고한다.

## 테스트가 들어가는 곳

**경계**는 테스트가 호출하는 공개 인터페이스다. 내부로 들어가지 않고 행동을 관찰한다. 테스트는 경계에 있으며, 내부를 대상으로 하지 않는다.

**사전에 합의한 경계에서만 테스트한다.** 어떤 테스트를 작성하기 전에 테스트할 경계를 적고 사용자와 확인한다. 사용자가 확인하지 않은 경계에서는 테스트를 작성하지 않는다. 모든 것을 테스트할 수는 없다. 경계를 미리 합의하면 테스트 작성자는 모든 엣지 케이스 대신 중요 경로와 복잡한 로직에 테스트 노력을 집중한다.

질문하라: "공개 인터페이스가 무엇이며, 어디를 테스트해야 하는가?"

## 안티 패턴

- **구현에 결합됨**: 내부 협력자를 모킹하거나, private 메서드를 테스트하거나, 사이드 채널(인터페이스 대신 데이터베이스를 조회)로 검증한다. 징후: 행동이 바뀌지 않았는데 리팩터링하면 테스트가 깨진다.
- **동어반복**: 단언이 코드와 같은 방식으로 기대값을 다시 계산한다(`expect(add(a, b)).toBe(a + b)`, 같은 방식으로 만든 수동 스냅샷, 자기 자신과 같다고 단언한 상수). 그래서 테스트가 구조상 통과하며 코드와 다른 결과를 낼 수 없다. 기대값은 코드와 별도로 확인한 기준값이어야 한다. 알려진 올바른 리터럴, 실제 예제, 명세를 기준으로 삼는다.
- **수평 분할**: 모든 테스트를 먼저 쓰고 그다음 모든 구현을 쓰는 방식이다. 대량의 테스트는 상상한 행동을 검증한다.

  그런 테스트는 사용자에게 보이는 행동이 아니라 구조의 겉모양을 확인한다. 테스트는 실제 변경에 둔감해진다. 구현을 이해하기 전에 테스트 구조를 확정한다.

  대신 **수직 슬라이스**로 작업한다. 하나의 테스트 → 하나의 구현 → 반복. 각 테스트는 이전 사이클에서 알게 된 내용을 반영하는 **tracer bullet**이다.

## 루프의 규칙

- **green보다 먼저 red.** 먼저 실패하는 테스트를 쓰고, 통과할 만큼만 코드를 쓴다. 미래의 테스트를 예상하거나 추측성 기능을 추가하지 않는다.
- **한 번에 한 슬라이스.** 사이클마다 하나의 경계, 하나의 테스트, 하나의 최소 구현.
- **리팩터링은 루프의 일부가 아니다.** 리팩터링은 red → green 구현 루프가 아니라 검토 단계(`/vibe-review` 스킬 참고)에 속한다.
