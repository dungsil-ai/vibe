# 범위 밖 지식 베이스

저장소의 `docs/agents/out-of-scope/` 디렉터리는 거부된 기능 요청의 영구 기록을 보관한다. 두 목적을 한다:

1. **조직의 기억**: 기능이 왜 거부되었는지, 이슈가 닫혀도 이유가 사라지지 않게
2. **중복 제거**: 이전 거부와 일치하는 새 이슈가 들어오면, 스킬이 이전 결정을 다시 논의하지 않고 관리자에게 알린다.

## 목차

- 디렉터리 구조
- 파일 형식: 기록 템플릿, 파일 이름 짓기, 이유 쓰기
- `docs/agents/out-of-scope/`를 확인할 때
- `docs/agents/out-of-scope/`에 쓸 때
- 범위 밖 파일 갱신 또는 제거

## 디렉터리 구조

```
docs/agents/out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

**개념**마다 한 파일을 만든다. 이슈마다 파일을 만들지 않는다. 같은 개념을 요청하는 둘 이상의 이슈는 한 파일에 묶는다.

## 파일 형식

읽기 쉬운 문체를 쓴다. 처음 보는 사람도 이유를 이해하고 활용할 수 있도록 문단, 코드 예시, 사례를 넣는다. 데이터베이스 항목보다 짧은 설계 문서처럼 쓴다.

```markdown
# 다크 모드

이 프로젝트는 다크 모드나 사용자 대면 테마를 지원하지 않는다.

## 왜 범위 밖인가

렌더링 파이프라인은 `ThemeConfig`에 정의된 단일 색 팔레트를
가정한다. 여러 테마를 지원하려면 다음이 필요하다:

- 전체 컴포넌트 트리를 감싸는 테마 컨텍스트 제공자
- 컴포넌트마다 테마를 고려하는 스타일 해석
- 사용자 테마 선호도의 영속화 계층

이것은 프로젝트의 콘텐츠 작성 초점과 일치하지 않는 중요한
아키텍처 변경이다. 테마는 출력을 내장하거나 재배포하는
다운스트림 소비자의 관심사다.

```ts
// 현재 ThemeConfig 인터페이스는 런타임 전환에 설계되지 않았다:
interface ThemeConfig {
  colors: ColorPalette; // 단일 팔레트, 빌드 시간에 해석
  fonts: FontStack;
}
```

## 이전 요청

- #42: "다크 모드 지원 추가"
- #87: "접근성을 위한 야간 테마"
- #134: "다크 테마 옵션"
```

### 파일 이름 짓기

개념을 나타내는 짧고 설명적인 kebab-case 파일 이름을 쓴다. 예를 들면 `dark-mode.md`, `plugin-system.md`, `graphql-api.md`가 있다. 디렉터리 목록을 훑어보는 사람도 파일을 열지 않고 거부된 요청이 무엇인지 알 수 있어야 한다.

### 이유 쓰기

이유는 본질적이어야 한다. "원하지 않는다"라고만 쓰지 말고 이유를 설명한다. 좋은 이유에는 다음을 든다:

- 프로젝트 범위나 철학 ("이 프로젝트는 X에 집중한다; 테마는 다운스트림 관심사다")
- 기술 제약 ("이것을 지원하려면 Y가 필요하고, 우리의 Z 아키텍처와 충돌한다")
- 전략 결정 ("B 대신 A를 쓰기로 했다. 왜냐하면...")

이유는 내구성이 있어야 한다. 일시적 상황을 참조하지 않는다("지금 너무 바쁘다"). 그것은 진짜 거부가 아니라 연기다.

## `docs/agents/out-of-scope/`를 확인할 때

트리아지 중(1단계: 맥락 수집), `docs/agents/out-of-scope/`의 모든 파일을 읽는다. 새 이슈를 평가할 때:

- 요청이 기존 범위 밖 개념과 일치하는지 확인
- 키워드가 아니라 개념 유사성으로 대조한다. "야간 테마"는 `dark-mode.md`와 일치
- 일치가 있으면, 관리자에게 일치한 기록을 알린다: "이것은 `docs/agents/out-of-scope/dark-mode.md`와 유사합니다. 이전에 [이유]로 거부했습니다. 여전히 같은 생각이신가요?"

관리자는 다음을 할 수 있다:

- **확인**: 관리자가 확인하면 에이전트가 새 이슈를 기존 파일의 "이전 요청" 목록에 추가하고 이슈를 닫는다
- **재고**: 에이전트가 범위 밖 파일을 삭제하거나 갱신한다. 에이전트는 이슈를 정상적으로 트리아지한다.
- **반대**: 관리자는 새 이슈가 기존 요청과 연결되어 있지만 별개라고 판단한다. 에이전트는 이슈를 정상적으로 트리아지한다.

## `docs/agents/out-of-scope/`에 쓸 때

**개선**(버그가 아닌 요청)을 `wontfix`로 거부한 경우에만 여기에 기록한다. 이것은 이슈와 똑같이 개선 PR에도 적용된다. 거부된 PR은 같은 요청이 새 코드로 돌아오지 않게 여기에 기록한다.

무언가가 **이미 구현되어** `wontfix`로 닫힐 때는 여기에 쓰지 **않는다**. 그것은 거부된 것이 아니라 이미 구현한 기능이다. 이 내용을 기록하면 중복 검사에서 거부하지 않은 기능을 거부된 기능으로 잘못 분류한다. 대신 닫는 댓글에서 그 기능이 있는 위치를 가리킨다.

흐름:

1. 관리자가 기능 요청이 범위 밖이라고 결정
2. 일치하는 `docs/agents/out-of-scope/` 파일이 이미 있는지 확인
3. 있으면: 새 이슈를 "이전 요청" 목록에 덧붙임
4. 없으면: 개념 이름, 결정, 이유, 첫 번째 이전 요청으로 새 파일을 만듦
5. 이슈에 결정을 설명하고 `docs/agents/out-of-scope/` 파일을 언급하는 댓글 게시
6. `wontfix` 라벨로 이슈 닫기

## 범위 밖 파일 갱신 또는 제거

관리자가 이전에 거부한 개념의 결정을 바꾸면:

- `docs/agents/out-of-scope/` 파일을 삭제
- 스킬은 옛 이슈를 다시 열 필요가 없다. 옛 이슈는 역사적 기록이다
- 에이전트는 재고를 유발한 새 이슈를 정상적으로 트리아지한다
