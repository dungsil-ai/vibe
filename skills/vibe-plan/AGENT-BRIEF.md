# 에이전트 브리프 쓰기

이 문서는 일반 트리아지·티켓의 브리프에 적용한다. 명시적 실행계획 경로는 [EXECUTION-PLAN.md](EXECUTION-PLAN.md)를 따르며, 아래의 파일 경로·줄 번호 제한을 적용하지 않는다.

에이전트 브리프는 이슈나 PR이 `ready-for-agent`로 옮겨질 때 GitHub 이슈나 PR에 게시하는 구조화된 댓글이다. 사람이 지켜보지 않아도 작업하는 AFK(away from keyboard) 에이전트는 이 브리프를 작업 기준으로 삼는다. 원본 본문과 논의는 맥락이고, 브리프는 에이전트가 따라야 할 작업 계약이다.

브리프는 에이전트가 해야 할 일을 서술한다. 이 원칙은 이슈와 PR 모두에 적용된다. 이슈에서는 에이전트가 변경을 처음부터 만든다.

PR에서는 에이전트가 기존 diff에서 남은 일을 마무리하거나 고친다. 에이전트는 빠진 부분을 채우고 검토 의견을 반영한다. 두 경우의 원칙은 같다. 아래 PR 예시에서 차이를 확인할 수 있다.

## 목차

- 원칙: 내구성, 절차가 아닌 행동, 완전한 완료 조건, 명시적 범위
- 템플릿: 댓글로 게시할 브리프 구조
- 예시: 버그, 개선, PR의 좋은 브리프와 나쁜 브리프

## 원칙

### 정밀성보다 내구성

이슈는 `ready-for-agent` 상태에서 대기할 수 있다. 그 사이 코드베이스가 바뀐다. 파일 이름이 바뀌고 옮겨지거나 리팩터링되어도 유용하도록 브리프를 쓴다.

- 인터페이스, 타입, 행동 계약을 서술한다
- 에이전트가 찾거나 수정해야 할 구체적인 타입, 함수 서명, 설정 형태를 브리프에 명시한다
- 파일 경로를 참조하지 않는다. 파일 경로가 바뀌면 브리프가 틀려지기 때문이다
- 줄 번호를 참조하지 않는다
- 브리프를 쓸 때의 구현 구조가 계속 같을 것이라고 가정하지 않는다

### 절차가 아닌 행동

브리프에는 시스템이 해야 할 일을 쓴다. 구현 방법은 적지 않는다. 에이전트는 코드베이스를 새로 살핀다. 구현 방식은 에이전트가 직접 정한다.

- **좋음:** "`SkillConfig` 타입은 `CronExpression` 타입의 선택적 `schedule` 필드를 받아야 한다"
- **나쁨:** "src/types/skill.ts를 열고 42번 줄에 schedule 필드를 추가하라"
- **좋음:** "사용자가 인자 없이 `triage list`를 실행하면, 주의가 필요한 이슈 요약이 보여야 한다"
- **나쁨:** "메인 핸들러 함수에 switch 문을 추가하라"

### 완전한 완료 조건

에이전트는 완료 시점을 알아야 한다. 모든 에이전트 브리프에는 구체적이고 테스트 가능한 완료 조건이 필요하다. 각 조건은 독립적으로 검증할 수 있어야 한다.

- **좋음:** "`gg issue list --label needs-triage`를 실행하면 초기 분류를 거친 이슈가 반환된다"
- **나쁨:** "트리아지가 올바르게 동작해야 한다"

### 명시적 범위 경계

범위 밖인 항목을 설명한다. 이 내용은 에이전트가 요청하지 않은 기능을 덧붙이거나 인접 기능의 동작을 멋대로 바꾸는 일을 막는다.

## 템플릿

```markdown
## 에이전트 브리프

**범주:** bug / enhancement
**요약:** 무엇이 일어나야 하는지 한 줄로 쓴다

**현재 동작:**
지금 일어나는 동작을 쓴다. 버그라면 망가진 동작을 설명한다.
개선 요청이라면, 에이전트가 기능을 추가하기 전에 코드가 어떻게 동작하는지 쓴다.

**원하는 동작:**
에이전트가 작업을 끝낸 뒤 어떤 동작이 일어나야 하는지 쓴다.
예외 상황과 오류 조건을 구체적으로 쓴다.

**핵심 인터페이스:**
- `TypeName`: 무엇을 바꿔야 하는지와 바꾸는 이유
- `functionName()` 반환 타입: 지금 반환하는 타입과 반환해야 하는 타입
- 설정 형태: 필요한 새 설정 옵션

**완료 조건:**
- [ ] 구체적이고 테스트 가능한 조건 1
- [ ] 구체적이고 테스트 가능한 조건 2
- [ ] 구체적이고 테스트 가능한 조건 3

**범위 밖:**
- 이 이슈에서 변경하거나 다루지 않아야 할 것
- 관련 있어 보이지만 별개인 인접 기능
```

## 예시

### 좋은 에이전트 브리프(버그)

```markdown
## 에이전트 브리프

**범주:** bug
**요약:** 스킬 설명 자르기가 단어 중간에서 끊겨 깨진 출력을 만든다

**현재 동작:**
스킬 설명이 1024자를 넘기면, 단어 경계와 무관하게 정확히
1024자에서 잘린다. 이것은 단어 중간에서 끝나는 설명을 만든다
(예. "사용자가 confi를 원할 때").

**원하는 동작:**
자르기는 1024자 이전의 마지막 단어 경계에서 끊고
자르기를 나타내기 위해 "..."를 붙여야 한다.

**핵심 인터페이스:**
- `SkillMetadata` 타입의 `description` 필드는 타입을 바꿀 필요가 없다.
  이 필드에 값을 채우는 검증과 처리 로직은 단어 경계에서만 잘라야 한다
- `SKILL.md` frontmatter를 읽고 설명을 추출하는 모든 함수

**완료 조건:**
- [ ] 1024자 미만 설명은 변하지 않는다
- [ ] 1024자 초과 설명은 1024자 이전의 마지막 단어 경계에서 잘린다
- [ ] 잘린 설명은 "..."로 끝난다
- [ ] "..." 포함 총 길이는 1024자를 넘지 않는다

**범위 밖:**
- 1024자 제한 자체를 바꾸는 것
- 여러 줄 설명 지원
```

### 좋은 에이전트 브리프(개선)

```markdown
## 에이전트 브리프

**범주:** enhancement
**요약:** 거부된 기능 요청을 추적할 수 있도록 `docs/agents/out-of-scope/` 디렉터리를 지원한다

**현재 동작:**
기능 요청이 거부되면, 이슈는 `wontfix` 라벨과
댓글로 닫힌다. 결정이나 이유의 영구 기록이 없다.
나중에 비슷한 요청이 다시 들어오면 관리자는 이전 논의를 기억하거나 검색해야 한다.

**원하는 동작:**
에이전트는 거부된 기능 요청의 결정과 이유, 그 기능을 요청한 모든 이슈의 링크를 `docs/agents/out-of-scope/<concept>.md` 파일에 기록해야 한다.
새 이슈를 트리아지할 때 에이전트는 이 디렉터리에서 일치하는 기록을 찾아야 한다.

**핵심 인터페이스:**
- `docs/agents/out-of-scope/`의 Markdown 파일 형식: 각 파일은
  `# Concept Name` 제목, `**Decision:**` 줄, `**Reason:**` 줄,
  이슈 링크가 있는 `**이전 요청:**` 목록을 가져야 한다
- 트리아지 워크플로는 모든 `docs/agents/out-of-scope/*.md` 파일을 먼저 읽어야 한다. 들어오는 이슈와 기록된 개념이 비슷한지 대조해야 한다

**완료 조건:**
- [ ] 기능을 wontfix로 닫으면 `docs/agents/out-of-scope/`에 파일을 만들거나 갱신한다
- [ ] 파일은 결정, 이유, 닫힌 이슈로의 링크를 포함한다
- [ ] 일치하는 `docs/agents/out-of-scope/` 파일이 이미 있으면, 새 이슈는
      중복을 만드는 대신 "이전 요청" 목록에 덧붙인다
- [ ] 트리아지 중 에이전트는 기존 `docs/agents/out-of-scope/` 파일을 확인하고, 새 이슈가 이전 거부와 일치하면 관리자에게 그 기록을 알린다

**범위 밖:**
- 자동 대조(사람이 일치를 확인)
- 이전에 거부된 기능 다시 열기
- 버그 신고(이 디렉터리에는 거부한 개선 요청만 기록한다)
```

### 좋은 에이전트 브리프(PR)

PR의 경우, "현재 동작"에는 diff의 상태를 쓴다. 브리프는 에이전트에게 변경을 처음부터 새로 만들지 말고 기존 diff에서 남은 일을 마무리하거나 고치도록 요청한다.

```markdown
## 에이전트 브리프

**범주:** enhancement
**요약:** 기여자의 `triage list`용 `--json` 출력 플래그를 마무리하라

**현재 동작:**
PR은 이슈 목록을 JSON으로 직렬화하는 `--json` 플래그를 추가한다.
정상 경로는 동작하고 diff는 프로젝트의 명령 구조와 일치한다. 다음 두 문제가 남는다. 에러 경로는 JSON이 아닌 일반 텍스트를 출력하고, 새 플래그를 검증하는 테스트가 없다.

**원하는 동작:**
`--json`을 쓰면 에러를 포함한 모든 출력이 stdout에 올바른 JSON 형식으로 나온다.
명령의 종료 코드는 변하지 않는다. 플래그가 없을 때 기존 사람용 출력은
그대로다.

**핵심 인터페이스:**
- 명령의 에러 경로는 `--json`에서 일반 텍스트 에러 대신
  `{ "error": string }`을 내야 한다
- PR이 이미 추가한 기존 직렬 변환기를 재사용한다. 두 번째 직렬 변환기를 새로 만들지 않는다

**완료 조건:**
- [ ] `triage list --json`이 성공과 에러 모두에 대해 유효한 JSON을 낸다
- [ ] 종료 코드가 `--json` 없이 실행한 같은 명령의 종료 코드와 같다
- [ ] 테스트가 `--json` 성공 출력과 에러 사례 한 가지를 검증한다
- [ ] 기본(비-JSON) 출력은 바이트 단위로 변하지 않는다

**범위 밖:**
- 다른 명령에 `--json` 추가
- PR이 이미 정의한 성공 페이로드의 JSON 형태 바꾸기
```

### 나쁜 에이전트 브리프

```markdown
## 에이전트 브리프

**요약:** 트리아지 버그 고치기

**할 일:**
트리아지가 망가졌다. 메인 파일을 보고 고쳐라.
150번 줄쯤의 함수가 문제다.

**바꿀 파일:**
- src/triage/handler.ts (150번 줄)
- src/types.ts (42번 줄)
```

이것이 나쁜 이유:
- 범주가 없다
- 모호한 설명 ("트리아지가 망가졌다")
- 파일 경로와 줄 번호를 브리프에 쓰면 경로가 바뀔 때 내용이 틀려진다
- 완료 조건이 없다
- 범위 경계가 없다
- 현재 vs 원하는 동작의 서술이 없다
