# 변경 검토하기

이 스킬은 `HEAD`와 사용자가 제시한 고정점 사이의 변경 내용을 따로 검토한다.

- **Standards**: 코드가 이 저장소의 문서화된 코딩 표준을 따르는가?
- **Spec**: 코드가 출처가 된 이슈, 제품 요구사항 문서(Product Requirements Document, PRD) 또는 명세를 충실히 구현하는가?
- **Risk**: 추가·수정 코드가 버그, 보안 문제, 개발 환경 파괴, 또는 피처 게이트 누수를 만드는가?

Standards와 Spec은 기본 축이다. 사용자가 위험 감사·thermos·thermo nuclear를 요청했거나 변경이 보안, 인증, 권한, 영속성, 트랜잭션 또는 외부 연동을 건드릴 때만 Risk를 켠다. 켠 축은 별도의 병렬 서브에이전트가 검토한다. 서브에이전트는 서로의 맥락을 섞지 않는다. 이 스킬은 발견 사항을 모은다.

Spec은 **빠른 검토**다. 서브에이전트 하나가 명세와 diff를 비교해 빠진 요구사항, 범위 확장, 잘못된 구현을 400단어 안에 보고한다.

정식 요구사항 판정에는 항목별 상태, 분리된 증거 영역, 독립 검토자의 통과 여부, `PASS`/`FAIL`/`NEEDS_REVIEW` 집계가 포함된다. 사용자가 이런 판정을 요청하면 같은 요구사항에 `/rq`를 별도로 실행한다. `/rq`를 실행하면 Spec을 대체한다. 둘을 실행해 결과를 합치지 않는다. 사용자가 직접 호출한 `/vibe-review`는 고위험이라는 이유만으로 `/rq`를 자동 호출하지 않는다.

[설정 문서와 기본값](../vibe-init/references/defaults.md)을 읽는다. 설정이 없으면 초기화를 요구하지 않고 로컬 Markdown에서 명세와 티켓을 찾아 검토한다. 검토는 읽기 전용이므로 기본값을 적용해도 설정, 명세, 티켓 파일을 만들거나 수정하지 않는다. 필요한 명세가 실제로 없을 때만 아래 명세 탐색 규칙에 따라 한계를 보고한다.

## 과정

### 1. 고정점 고정하기

사용자가 고정점으로 지정할 수 있는 값에는 커밋 SHA, 브랜치 이름, 태그, `main`, `HEAD~5`가 있다. 다른 스킬이 이 스킬을 호출하며 고정점을 넘기면 그 값을 쓴다. `/vibe-implement`는 시작 전에 기록한 커밋을 넘긴다. 호출자가 고정점을 넘기면 사용자에게 묻지 않는다. 사용자나 호출자 어느 쪽도 고정점을 제공하지 않았을 때만 사용자에게 묻는다.

diff 명령을 한 번 잡는다: `git diff <fixed-point>...HEAD`(점 세 개, 비교가 merge-base 기반이 되도록). 커밋 목록은 `git log <fixed-point>..HEAD --oneline`으로도 적어둔다.

검토를 이어가기 전에 `git rev-parse <fixed-point>`로 고정점이 유효한 ref인지 확인한다. ref가 유효하지 않거나 diff가 비어 있으면 이 단계에서 검토를 중단하고 병렬 서브에이전트를 실행하지 않는다.

### 2. 명세 출처 식별하기

출처 명세를 다음 순서로 찾는다:

1. 커밋 메시지의 이슈 참조(`#123`, `Closes #45`, GitLab `!67`): `docs/agents/issue-tracker.md`의 워크플로로 가져온다.
2. 사용자가 인수로 넘긴 경로.
3. 브랜치 이름이나 기능과 일치하는 `docs/`, `specs/` 또는 `.agents/plans/` 아래의 PRD 또는 명세 파일.
4. 아무것도 없으면, 사용자에게 명세 위치를 묻는다. 없다고 하면, **Spec** 서브에이전트는 건너뛰고 "명세 없음"을 보고한다.

### 3. Risk 실행 여부 결정하기

서브에이전트를 실행하기 전에 Risk를 켤지 결정한다. 다음 중 하나면 켠다:

- 사용자가 위험 감사, thermos, 또는 thermo nuclear를 요청했다.
- diff가 보안, 인증, 권한, 영속성, 트랜잭션, 또는 외부 연동을 건드린다.

그 외에는 Risk를 끈다. 명세가 없어도 Risk 실행 조건에는 영향이 없다. 고위험 신호는 Risk를 켜는 조건이지 `/rq`를 자동 호출하는 조건이 아니다.

### 4. 표준 출처 식별하기

저장소에서 코딩 방법을 문서화한 파일을 모두 찾는다. 예를 들면 `CODING_STANDARDS.md`와 `CONTRIBUTING.md`다.

위반을 평가할 때 저장소의 실제 검사 명령, 린터 설정, 훅과 CI 연결을 확인한다. 설정 파일이 있다는 이유만으로 검사된다고 간주하지 않는다. 도구가 이미 유효하게 강제하는 규칙은 중복 보고하지 않는다.

발견한 위반은 **기계적 검사 가능**과 **판단 필요**로 구분한다. 금지 API, import 형태, 파일 위치처럼 반복 판정할 수 있는 위반은 기존 검사 도구를 이용한 자동 검사 후보로 제안한다. 검사가 있지만 연결이 빠졌거나 작동하지 않으면 새 검사를 제안하지 않고 그 문제를 지적한다. 문맥에 따른 설계·일관성 판단에는 문서화된 표준을 사용한다. 자동 검사 제안은 코드 위반 자체와 구분하는 후속 권고다. 제안만으로 미해결 위반이나 머지 차단으로 판정하지 않는다.

검사 부재만으로 변경과 무관한 저장소 전체 수정을 요구하지 않으며, 검토 중 린터·훅·CI·표준 파일을 수정하지 않는다. 세션 단위로 환경을 회고해야 하면 이 스킬에서 환경을 회고하지 않고 사용자에게 `/vibe-hoego` 실행을 안내한다.

저장소 표준에 더해 Standards 축은 항상 **스멜 기준선**도 적용한다. 이 기준선은 Fowler가 _Refactoring_ 3장에서 정리한 코드 스멜 고정 목록이다. 저장소가 아무것도 문서화하지 않았을 때도 이 기준선을 적용한다. 다음 두 규칙이 스멜 기준선과 저장소 표준의 관계를 정한다:

- **저장소가 우선한다.** 문서화된 저장소 표준이 스멜 기준선보다 우선한다. 저장소 표준이 기준선에서 지적하는 스멜을 허용하면 그 스멜은 보고하지 않는다.
- **항상 판단 영역.** 각 스멜은 "가능한 Feature Envy"처럼 라벨을 붙인 휴리스틱이다. 스멜은 절대 경질 위반이 아니다. 도구가 이미 강제하는 규칙은 여기의 모든 표준처럼 건너뛴다.

각 스멜은 두 부분으로 설명한다. 먼저 어떤 코드가 스멜에 해당하는지 설명한다. 다음으로 diff에서 발견한 코드를 어떻게 고칠지 설명한다:

- **수상한 이름 (Mysterious Name)**: 함수, 변수 또는 타입 이름이 하는 일이나 담는 내용을 나타내지 않는다. 이름을 기능이나 저장 내용에 맞게 바꾼다. 이름으로 기능을 정확히 나타낼 수 없으면 설계가 불분명하다.
- **중복 코드 (Duplicated Code)**: 변경 내용의 둘 이상의 hunk나 파일에 같은 논리 형태가 나타난다. 같은 형태를 공유 코드로 추출해 양쪽에서 호출한다.
- **기능 질투 (Feature Envy)**: 메서드가 자기 객체의 데이터보다 다른 객체의 데이터를 더 많이 사용한다. 그 메서드를 데이터가 있는 객체로 옮긴다.
- **데이터 뭉치 (Data Clumps)**: 같은 필드나 매개변수를 함께 사용하는 코드가 반복된다. 이들을 하나의 타입으로 묶어 전달한다.
- **원시 타입 집착 (Primitive Obsession)**: 별도 타입이 필요한 도메인 개념을 원시값이나 문자열로 나타낸다. 그 개념을 표현하는 작은 타입을 만든다.
- **반복 스위치 (Repeated Switches)**: 같은 타입을 검사하는 `switch`나 `if-else` 연쇄가 변경 내용 전체에서 반복된다. 다형성을 쓰거나 공유 map 하나로 대체한다.
- **산탄총 수술 (Shotgun Surgery)**: 하나의 변경 때문에 둘 이상의 파일을 수정해야 한다. 함께 바뀌는 코드를 하나의 모듈로 모은다.
- **발산적 변경 (Divergent Change)**: 한 파일이나 모듈을 서로 무관한 둘 이상의 이유로 수정한다. 모듈마다 변경 이유가 하나만 남도록 나눈다.
- **추측성 일반화 (Speculative Generality)**: 추상화, 매개변수 또는 훅이 명세에서 요구하지 않은 기능을 지원한다. 불필요한 코드를 삭제한다. 실제 필요가 확인될 때까지 코드를 인라인 상태로 둔다.
- **메시지 연쇄 (Message Chains)**: 호출자가 의존해서는 안 되는 긴 `a.b().c().d()` 탐색이다. 탐색 경로를 첫 객체의 메서드 하나 뒤에 숨긴다.
- **중간자 (Middle Man)**: 위임 동작이 자체 작업보다 많은 클래스나 함수다. 그런 클래스나 함수를 없애고 실제 대상을 직접 호출한다.
- **거절된 유산 (Refused Bequest)**: 서브클래스나 구현체에서 사용하는 기능보다 무시하거나 재정의하는 상속 기능이 더 많다. 상속 대신 합성을 쓴다.

### 5. 켠 축을 병렬로 실행하기

켠 축의 `Agent` 도구 호출은 한 메시지에서 병렬로 실행한다. 모두 `general-purpose` 서브에이전트를 쓴다. Spec이 없으면 Spec을 실행하지 않는다. 3단계에서 Risk를 끄기로 했으면 Risk를 실행하지 않는다.

**Standards 서브에이전트 프롬프트**에 다음 내용을 넣는다:

- 전체 diff 명령과 커밋 목록.
- 4단계에서 찾은 표준 출처 파일 목록과 4단계의 스멜 기준선 전체를 붙여 넣는다. 서브에이전트는 다른 접근 수단이 없다.
- 4단계에서 확인한 검사 명령, 설정, 훅, CI 경로와 연결 상태.
- 서브에이전트에게 다음 규칙을 준다:
  - 각 발견을 기계적 검사 가능 또는 판단 필요로 구분한다.
  - 반복 판정이 가능한 위반은 기존 검사 도구를 우선해 자동 검사 후보로 제안한다. 이 제안은 같은 발견 안의 후속 권고로 쓴다.
  - 제안만으로 머지를 차단하지 않는다.
  - 검사를 새로 만들거나 설정을 수정하지 않는다.
- 지시문: "위반이나 스멜이 있는 파일과 hunk마다 다음을 보고한다. (a) diff에서 문서화된 표준을 위반한 위치를 모두 찾아 표준 파일과 규칙을 함께 인용한다. (b) 기준선 스멜을 발견하면 이름과 hunk를 인용한다. 경질 위반인지 판단 영역인지 명확하게 나눈다.

  문서화된 표준 위반은 경질 위반일 수 있다. 기준선 스멜은 항상 판단 영역이다. 문서화된 저장소 표준이 기준선보다 우선한다. 도구가 이미 강제하는 규칙은 건너뛴다. 400단어 안에서 쓴다."

**Spec 서브에이전트 프롬프트**에 다음 내용을 넣는다:

- diff 명령과 커밋 목록.
- 명세의 경로나 가져온 내용.
- 지시문: "다음을 보고한다. (a) 명세가 요구했지만 빠졌거나 일부만 구현한 요구사항, (b) diff에서 명세가 요구하지 않은 동작(범위 확장), (c) 구현된 것처럼 보이지만 잘못 구현한 요구사항. 각 발견마다 근거가 되는 명세 줄을 인용한다. 400단어 안에서 쓴다."

명세가 없으면, Spec 서브에이전트를 건너뛰고 최종 보고서에 이를 적는다.

**Risk 서브에이전트 프롬프트**는 3단계에서 Risk를 켠 경우에만 작성한다:

- 전체 diff 명령과 커밋 목록, 위험 판단에 필요한 변경 파일 내용.
- 지시문: "추가·수정 코드만 감사한다. (a) 버그와 기존 기능 파괴, (b) 보안 문제, (c) 개발 환경 파괴, (d) 피처 게이트 누수를 보고한다. 개발 환경 파괴에는 비밀, 환경 변수, 포트를 바꾸는 변경과 새 필수 수동 설치가 포함된다. 패키지 매니저로 의존성을 추가하는 일은 그 자체로 개발 환경 파괴가 아니다. 저장소에 피처 게이트가 없으면 피처 게이트 누수를 건너뛴다. 분기가 기능을 의도적으로 끄고 그 영향이 의도한 범위를 벗어나지 않으면 보고하지 않는다.

  우선순위를 과장하지 않는다. 확인할 수 있는 코드를 끝까지 추적한다. 확인하지 못한 가설은 발견 사항으로 보고하지 않는다. 자체 감사를 마친 뒤에만 PR/MR 토론이 있으면 읽는다. 토론에 나온 기존 검토 결과 중 타당한 발견 사항만 반영한다. 특정 봇 이름을 조건으로 삼지 않는다.

  파일과 hunk, 근거를 인용한다. 400단어 안에서 쓴다."

### 6. 집계하기

보고서를 `## Standards`, 있으면 `## Spec`, 켰으면 `## Risk` 제목 아래에 있는 그대로 또는 가볍게 다듬어 제시한다. 발견 사항을 축 사이에서 합치거나 재순위하거나, 겹침에 가중치를 주지 **않는다**.

한 줄 요약으로 끝낸다. 요약에는 실행한 축별 발견 사항의 총수를 쓴다. 각 축에 가장 심각한 발견 사항이 있으면 그것도 쓴다. 축 사이에서 가장 심각한 발견 하나를 고르지 않는다.

### 7. 읽기 전용 검토 계약

직접 검토와 다른 워크플로가 호출한 검토는 **읽기 전용**이다. 유일한 결과물은 6단계의 분리된 축 보고서다:

- 검토에서 발견 사항이 없으면 0건이라고 보고한다. 통과 판정은 변경 반영, 갱신, 종료 권한을 주지 않는다.
- 발견 사항이 있으면 그 내용을 보고한다. 명세가 없으면 그 한계도 보고한다.
- 다음 작업은 절대 하지 않는다:
  - 이슈나 PR 본문이나 인수 박스를 편집하지 않는다.
  - 댓글을 게시하지 않는다.
  - 라벨이나 상태를 바꾸지 않는다.
  - 작업을 닫거나 다시 열지 않는다.
  - 다른 트래커나 저장소를 바꾸지 않는다.
  - 외부 부작용을 만들지 않는다.

이 스킬은 인수 체크리스트를 켜지 않는다. 깨끗한 검토 뒤, 사람이 머지하기 전에 `/vibe-implement`가 체크리스트를 켠다. 검토는 체크리스트 갱신을 머지 뒤로 미루지 않는다. 이슈 닫기는 체크리스트와 별개이며 이 스킬의 범위가 아니다.

## 왜 축을 분리하는가

변경은 한 축에서는 통과하고 다른 축에서는 실패할 수 있다:

- 코드가 모든 코딩 표준을 따르면서 잘못된 동작을 구현하면 Standards 검토를 통과하지만 Spec 검토는 통과하지 못한다.
- 이슈가 요구한 기능을 정확히 구현하지만 프로젝트 관례를 따르지 않는 코드는 Spec 검토를 통과하고 Standards 검토에서 실패한다.
- 표준과 명세를 만족하지만 인증 우회를 만드는 코드는 Standards와 Spec 검토를 통과하고 Risk 검토에서 실패 판정을 받는다.

분리해서 보고하면 한 축의 결과 때문에 다른 축의 결과를 놓치지 않는다.
