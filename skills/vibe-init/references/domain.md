# 도메인 문서

엔지니어링 스킬이 코드베이스를 탐색할 때 이 저장소의 도메인 문서를 어떻게 활용해야 하는지.

## 탐색 전, 다음을 읽는다

- 저장소 루트의 **`CONTEXT.md`**, 또는
- 저장소 루트에 **`CONTEXT-MAP.md`**가 있으면 — 컨텍스트마다 하나의 `CONTEXT.md`를 가리킨다. 주제와 관련된 각 파일을 읽는다.
- **`docs/adr/`** — 곧 작업할 영역과 관련된 ADR을 읽는다. 다중 컨텍스트 저장소에서는 컨텍스트별 결정을 위해 `src/<context>/docs/adr/`도 확인한다.

이 파일들 중 어느 것이든 없으면 **조용히 진행**한다. 없다고 지적하지 않고, 미리 만들라고 제안하지도 않는다. `/vibe-modeling` 스킬(`/vibe-plan`과 `/vibe-refactor`를 통해 호출)은 용어나 결정이 실제로 확정될 때 그때그때 만든다.

## 파일 구조

단일 컨텍스트 저장소(대부분의 저장소):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

다중 컨텍스트 저장소(루트에 `CONTEXT-MAP.md`가 있는 경우):

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← 시스템 전체 결정
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← 컨텍스트별 결정
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 용어집 어휘 사용

출력에서 도메인 개념을 이름 지을 때(이슈 제목, 리팩터 제안, 가설, 테스트 이름에서) `CONTEXT.md`에 정의된 용어를 그대로 사용한다. 용어집이 명시적으로 피하는 동의어로 넘어가지 않는다.

용어가 한국어, 영어 또는 혼합 표기여도 번역, 음역, 풀어쓰기, 일반화, 중립화 또는 동의어 교체를 하지 않는다. 관련 ADR이나 `docs/agents/`가 용어를 더 좁게 정했다면 그 표기도 같은 방식으로 보호한다.

필요한 개념이 아직 용어집에 없다면 신호다 — 프로젝트가 쓰지 않는 말을 지어낸 것(다시 생각)이거나 실제 빈틈(`/vibe-modeling`에 기록)이다.

## ADR 충돌 표시

> _ADR-0007(이벤트 소스 주문)과 모순 — 하지만 다시 논의할 가치가 있는 이유는…_
